Your first deployment

Inferra builds and deploys apps from GitHub pushes. This guide connects a repository, defines its spaces and app, and shows how to read the result.

PrerequisitesConfigurationSecretsCommit checksPostgresTroubleshooting

1. Have a repository and its admin ready

You need Git, a GitHub repository you can push to, and a GitHub repository admin who can install the Inferra App. Organization policy may require an organization owner to approve installation. Use a new repository for the complete Node example below, or adapt the app path, command and port to your existing app.

Not an admin? Copy this request and replace the repository and login:

Please install the Inferra GitHub App on OWNER/REPO:
https://api.dev.inferralab.com/v1/github/install
Please create GitHub Environments named prod, stage and preview,
and add MY_GITHUB_LOGIN with the developer role in .inferra/org.yaml.
Setup guide: https://inferralab.com/setup

GitHub repository admins become org owners. Other members and their space roles are declared in the file.

2. Install the App and CLI

Install the GitHub App Choose the repository you will deploy. Then follow the CLI download and checksum instructions.

Sign in to the dashboard with GitHub and create a personal token under Settings → Tokens. Paste it at the CLI prompt:

inferra login --api https://api.dev.inferralab.com

During the preview the platform runs at api.dev.inferralab.com, so pass it once; the CLI saves the address after login. If no org is available yet, continue with the configuration commit and target it afterward.

3. Create the app and org.yaml

In your repository root, run:

inferra init --name api

This writes .inferra/org.yaml and an optional .github/workflows/inferra-env.yml. It refuses to overwrite existing files unless you use --force. The workflow sends your GitHub variables and only the secrets you name (none by default); see step 4.

For the complete example, create package.json:

{
  "name": "inferra-first-app",
  "version": "1.0.0",
  "private": true,
  "scripts": { "start": "node server.js" }
}

Create server.js:

const http = require('node:http');
http.createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({ ok: true }));
}).listen(Number(process.env.PORT || 8080), '0.0.0.0');

Replace the generated .inferra/org.yaml with:

version: 1
spaces:
  prod:
    branch: main
  stage: {}
  preview:
    branches: "*"
apps:
  api:
    path: .
    port: 8080
    command: node server.js
    cpu: "0.5"
    memory: 512Mi
    health: /health

Download this org.yaml. The app listens on $PORT and /health returns HTTP 200. Buildpacks detect Node from package.json.

main deploys to prod. stage: {} has no branch and is available as a promotion target. To deploy pushes to staging, use stage: {branch: staging}. The preview pattern matches other branches, including names containing a slash; an exact branch mapping takes precedence. Each preview branch gets app copies in the preview space, removed when that branch is deleted. Each copy counts toward your app limit.

To add a non-admin, put members: {YOUR_GITHUB_LOGIN: developer} under each space they should use, replacing the login. See the complete field reference.

4. Choose how secret values reach Inferra

Create GitHub Environments named prod, stage and preview in the repository settings. Inferra reads repository Actions variables on each push; matching Environment variables override them. Secret names appear as placeholders. The GitHub App cannot read secret values.

Without the workflow, use the app’s Secrets section in the dashboard to add or set a value after the app exists. Developers and owners can write these values. Saving with restart applies the change to running instances; otherwise the next deployment applies it. Secret values are never returned by the API. The customer CLI lists names with inferra secrets api; it does not expose secret-writing commands.

Or keep secret values in GitHub

To have GitHub send secret values too, name them when you create the files. Only the secrets you list leave GitHub; with no --secret, none do:

inferra init --name api --secret API_KEY --secret DATABASE_URL

For an existing .inferra/org.yaml, regenerate just the workflow:

inferra init --workflow-only --force --secret API_KEY

Repeat --secret for every name to keep. A listed secret that isn't set in one Environment (say API_KEY only in prod) is skipped there, with a warning naming it. Removing a name removes its synced value in Inferra on the next run. The workflow sends GitHub variables and the listed secrets using GitHub OIDC (no stored token), with the sync Action pinned to an exact commit. It runs on pushes to main and on manual runs. Check that its api-url is https://api.dev.inferralab.com.

A value synced from GitHub takes precedence over a dashboard value and can't be replaced or deleted in Inferra while GitHub supplies it.

5. Commit and push

For a new repository using this example, commit these files and push main to your GitHub remote:

git add package.json server.js .inferra/org.yaml
git commit -m "Configure Inferra app"
git push -u origin main

If your local branch has another name, align it with spaces.prod.branch before pushing. The configuration must be present on the repository’s default branch. Future pushes to mapped branches build and deploy their apps.

6. Read the commit and open the app

Open the pushed commit in GitHub. These are status contexts and message templates from the server; angle brackets stand for actual values, not recorded demo output.

ContextStateDescription
inferra/configsuccessInferra configuration applied
inferra/configsuccessApplied with warning: <warning>
inferra/configfailureFirst validation problem from org.yaml
inferra/deploy/<app>pendingbuild started
inferra/deploy/<app>successdeployment live
inferra/deploy/<app>successunchanged since <7-character commit>, still live: <URL>
inferra/deploy/<app>success<N> secret(s) have no value yet: <names>
inferra/deploy/<app>failuredeployment <id> failed; see inferra logs
inferra/deploy/<app>errorsuperseded by a newer push
inferra/deploy/<app>errordeployment interrupted
inferra/pusherrorInferra couldn't process this push; it was retried and has been reported to Inferra support

A configuration success is not a deployment success. A live deployment can still report missing secret values. Live messages can append warnings or trial ends in <N> days. An unchanged app without a public hostname reports only unchanged since <commit>. Long descriptions are shortened for GitHub.

Follow a successful deployment’s details link to its HTTPS address, or use the URL shown by inferra apps status api. Find the actual org name before targeting it:

inferra orgs
inferra target YOUR_ORG/prod
inferra apps status api
inferra logs api
inferra logs api --follow

Replace YOUR_ORG with the name from inferra orgs. Logs include retained history when the platform’s archive is configured, plus running instances. Retention depends on the plan.

7. Add Postgres

Under apps.api, add:

services:
      orders:
        type: postgres
        plan: shared-small

Download the complete file with Postgres. The service catalog must allow this plan for your account; check the dashboard’s available services. Omitting version selects the current catalog version. A supported Postgres major can be selected explicitly, such as version: "17", subject to the live catalog.

git add .inferra/org.yaml
git commit -m "Bind Postgres to api"
git push
inferra services
inferra service status orders
inferra db logs orders
inferra env api

Inferra injects ORDERS_URL only into apps bound to orders. Configure your application’s Postgres client to use process.env.ORDERS_URL; the minimal HTTP example above does not query the database. The CLI shows the variable name with its value hidden. Removing the final service declaration schedules deletion; read the retention and restore limits first.

Next steps

  • Previews: push a branch matched by branches. Check your app and shared resource limits before creating more copies.
  • Promote a live image into staging: inferra promote api --from prod --to stage.
  • Roll back: inferra rollback api. This uses an earlier image with the app’s current variables and secrets, not historical configuration.
  • Billing: open Account → Billing in the dashboard. Review plan limits and trial terms.
  • Restore: request support assistance for deleted Postgres within its 7-day backup window; recovery depends on retained backups.
  • Uninstall: remove the App’s repository access in GitHub only when you intend to remove its Inferra org and resources. App removal triggers cleanup. Removing the local CLI alone does not remove deployments.
