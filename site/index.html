Your config

Change a file, change what runs.

Two short files, .inferra/org.yaml and .inferra/<branch>.yaml, say which branches to watch and which apps and services to deploy. Push, and Inferra makes it so.

mainproduction · inferralab.app
api liveworker runningorders · Postgres 17 new
feature/loginits own namespace · removed with the branch
api liveworker runningorders · its own copy new
What you wroteWhat happens
branches: [main, feature/*]A namespace for main and for every feature/ branch. Delete the branch and its namespace goes too.
postgres: ordersA Postgres 17 database in each of those namespaces, with backups.
services: [orders]api and worker are connected to the database. Its address is given to them automatically (as ORDERS_URL); no passwords to copy.

Git does the deploying.

A push to main updates its namespace. Each matched branch gets its own copy, removed when the branch is deleted.

  1. 1Push a branch

    Nothing to run locally. The CLI never deploys; git does.

  2. 2Checks on the commit

    One check per app on every commit: live, or the error. Unchanged apps are not rebuilt.

  3. 3Live app + database

    A copy of your apps, with a preview Postgres and private network kept apart from production. Delete the branch and the copy is gone.

Questions, answered.

Inferra in plain words.

What is Inferra?

A platform for real production applications. APIs, web apps and background workers, built straight from your repo. Postgres next to each app, a preview for every branch, and every app isolated from the server and from other apps. Connect a GitHub repository and push; Inferra runs the servers, HTTPS, scaling and patching.

How is Inferra different from Vercel?

Vercel is built mainly for frontend frameworks and functions, which have a maximum duration and scale down without traffic, so always-on background workers don’t fit. Its Postgres comes from partners such as Neon. Inferra runs long-running services and background workers with Postgres, a cache and buckets in the same place, with prepaid credits at simple per-unit prices. See the full comparison at inferralab.com/compare.

Is Inferra a Heroku alternative?

Yes. Like Heroku, you deploy with git push and buildpacks, with managed Postgres. Inferra adds previews for every matched branch, every app isolated from the server and other apps, built-in S3 buckets, and prepaid credits at simple per-unit prices.

Do I need a Dockerfile or Kubernetes knowledge?

No. Buildpacks detect your language and build a secure image from source. Inferra runs the servers, clusters, HTTPS, scaling and patching, so you only maintain your code.

Which languages and frameworks are supported?

Node.js, Python, Go, Java, Ruby, PHP, .NET and static sites, plus any app with a Procfile.

How are apps isolated?

Each app runs isolated with gVisor: it talks to a small screening kernel instead of the server’s real kernel. This isolation prevents a compromised app from reaching the host or other customers.

What is a background worker?

A background worker is a long-running process with no public web address, such as a queue consumer. Set run.process: worker in your branch file to run one.

Can I run background workers?

Yes. A Procfile worker selected in the branch file runs as a long-running background worker, next to your web apps and sharing their databases.

How does pricing work?

You pay for the CPU, memory and storage you reserve across your account, at simple per-unit prices, from prepaid credits. The first $5 every month is free per account, shared across its repos. A card on file is never charged unless you buy credits, and the bill can never go above the credits you added.

How are apps isolated and secured?

Every app runs isolated, so a broken or hacked app can't reach the server or anyone else's apps, free apps included. Each branch gets its own private network, and a database only accepts connections from the apps that use it.

Does Inferra work with AI coding assistants?

Yes. Inferra’s MCP server connects Claude Code, Codex, Cursor and VS Code to your apps: they read logs and metrics to explain problems, and propose configuration changes as pull requests you review.
