Security and data handling

Inferra isolates apps with gVisor, controls network access by space and service binding, and keeps secret values out of read APIs. This page describes the product controls and data retention.

Isolation and builds

Every app, including trial apps, runs isolated with gVisor. Spaces use separate namespaces and network policies. Buildpacks come from a mirrored catalog pinned by digest. Apps build from source with buildpacks, with no Dockerfile option. Every successful build is submitted for vulnerability scanning. A scan may be incomplete or unavailable; check its result before treating an image as scanned.

Build vulnerability scanning

Check the GitHub scan status and its report when available. An incomplete or unavailable scan is not a clean result. App security overrides in config v3 are not applied by the current deployment path; do not rely on YAML declarations alone to enforce a blocking policy.

Keep dependencies current and review the evidence before deployment. Questions about scanning: support@inferralab.com.

Network rules

TrafficRule for every app
InboundThrough Inferra’s HTTPS gateway on port 443, forwarded to the app’s PORT.
Within a spaceApps in the same space can reach each other.
OutboundAny public port, including external databases, SMTP and APIs. Private ranges and cloud metadata are blocked.
Managed Postgres and cacheOnly apps bound to the service can connect.
BucketsApp pod identity grants access; bucket keys are not handed to apps.

Secret values are write-only

Runtime variables and secrets are encrypted in the platform database with AES-GCM. Apps receive a versioned environment; switching versions rolls running instances. The API does not return secret values. Service connection values also stay hidden, including when a developer reveals ordinary environment variables.

The GitHub App reads variables and secret names, not secret values. Values reach Inferra through an explicitly configured environment workflow or a dashboard write. Read the selected-secret workflow before committing a generated workflow. Applications can still print their own secrets; keep credentials out of logs and public issue reports.

Deletion and restore

Account services are separate from app branches. Removing an app binding revokes its access; it does not delete an account-owned managed service. Unbind all apps before removing a service file from the private account repository. Service deletion follows service-specific snapshot and retention rules; do not assume all service types have backups.

Attached previews share the same service data unless you create a separate service for them. Deleting a preview does not delete account-owned managed services. For a restore request, email support@inferralab.com promptly with the service name and time to restore to. Never send credentials.

When the trial ends, apps stop and native services scale to zero. Data, config and URLs are kept for 30 days. Subscribe to Paid within that window to resume automatically. After 30 days everything is deleted; repository config stays untouched.

Cancel and service runs until the end of the paid month, then a 30-day hold, then deletion. Export data before the hold ends. Usage already used is not refundable; request a refund of the $25 within 7 days if usage was under $5. If a card fails, service-specific stop and recovery rules apply; read the payment failure schedule. Removing GitHub App access also triggers cleanup; export your data first.

Report a vulnerability

Use a private GitHub security advisory on inferra-AI/website. If private reporting is unavailable, open an issue asking for a private reporting channel; do not include exploit details, private data or credentials in a public issue.

Inferra does not hold SOC 2 or ISO 27001 certification. We do not claim HIPAA certification or a compliance guarantee for your application.
