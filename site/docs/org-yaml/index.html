Configuration v3: repo, app and account files

Configure branches in repo.yaml, apps in app.yaml and account services in a private account repository.

Where each file lives

Use config v3 for new deployments. Put .inferra/repo.yaml in the application repository and <folder>/.inferra/app.yaml in each app folder. A root app uses .inferra/app.yaml.

For account services, create a private GitHub repository named exactly <account>/.inferra and grant the Inferra GitHub App access. Put account.yaml and services/*.yaml at its root, not inside another .inferra directory. account.yaml is optional for a service-only setup. If present, list every connected app repository and provide all three quota values for the account and each repo.

A working web app

For repository shop, put this in .inferra/repo.yaml:

version: 3

Put this in api/.inferra/app.yaml. The app must listen on 0.0.0.0:3000 and answer /health:

version: 3
name: api
type: web
port: 3000
health:
  path: /health

Only the default branch runs. CPU defaults to 0.25 vCPU, memory to 256Mi and instances to 1. inferra init --app-dir api generates v3 files and an optional environment workflow; it never writes account.yaml.

Account settings

Example account.yaml at the root of the private <account>/.inferra repository:

version: 3
quota: {cpu: 4, memory: 8Gi, storage: 20Gi}
repos:
  shop:
    quota: {cpu: 4, memory: 8Gi, storage: 20Gi}

Only GitHub admins of that private repository can apply account and service changes. Pull requests validate proposals; an admin’s default-branch merge applies them. Keep secret values out of account settings.

Repository branches and previews

Repo rules are read from the application repository’s default branch for all deployments. To enable previews as well as main:

version: 3
branches:
  main: {}
  "feature/*":
    ttl: 7d
    quota: {cpu: 0.5, memory: 1Gi, storage: 2Gi}

With no branches map, only the default branch runs. With a nonempty map, only listed names and matching patterns run. An exact name wins; otherwise the longest pattern wins. Equal-length matches fail. A * does not cross a slash. TTL is allowed only on pattern keys and counts from the last accepted push. Branch deletion removes its apps and space, but does not delete account-owned managed services.

App settings and overrides

App files are read from the deployed branch. Keep the same app paths on deployed branches. Set CPU, memory and fixed instances directly in app.yaml; use type: worker for continuous work without a public URL, or type: job with a schedule for cron. Workers and jobs have no HTTP port or health check.

version: 3
type: worker
process: worker
cpu: 0.25
memory: 256Mi
instances: 1

Use app branches: entries with the same resolved branch keys as repo.yaml. Maps merge, scalars and lists replace, and null removes a key. App overrides do not stack across multiple matching patterns.

Account services and bindings

For account services, create a private GitHub repository named exactly <account>/.inferra and grant the Inferra GitHub App access. Put account.yaml and services/*.yaml at its root, not inside another .inferra directory. account.yaml is optional for a service-only setup. If present, list every connected app repository and provide all three quota values for the account and each repo.

For a Paid account, create services/orders.yaml in that private repository. This example attaches to application repository shop on main; replace both names with yours.

version: 3
name: orders
type: postgres
hosting: managed
size: db.t4g.micro
storage: 20Gi
engine_version: "17"
attach:
  shop:
    branches: [main]

Have a GitHub admin of the private account repository merge the service change first. Then add the binding to api/.inferra/app.yaml in the application repository:

version: 3
name: api
type: web
port: 3000
health:
  path: /health
services:
  orders: readwrite

Inferra supplies ORDERS_URL to the bound app. Never commit passwords. A binding grants access to an existing attached service; it does not create one. Multiple attached branches share the same data. For separate preview data, create a separately named service and attach it only to previews; data: shared does not create isolated data and is not available yet.

Trial accounts can use native Postgres, native Valkey and S3 buckets, but cannot use managed RDS. Native databases are rolling out; confirm availability with support@inferralab.com before depending on them. Custom image services are not available yet. SQS and DynamoDB on-demand are coming soon.

Quotas and billing

Branch quota entries in repo.yaml require cpu, memory and storage together. Exact branch quotas must fit the repo allocation when account.yaml exists. Pattern quotas apply to each matching preview. Quotas control resources; they are not a monthly spending limit. Start with $15 of trial credit or 14 days, whichever comes first. Card required; one trial per card. Paid is $25/month including $25 of usage. Usage beyond that is extra; unused included usage does not roll over.

Read billing, daily caps and payment timing. Do not rely on usage_budget to stop spending.

Environment, secrets and validation

Put ordinary values under env and only secret names under secrets. Later values win in this order: repo env, repo branch env, app env, app branch env. Repo secret names combine with the effective app list; app overrides replace the app list. Set values with inferra secrets set APP NAME or the dashboard, or explicitly sync them from GitHub. Never override PORT, INFERRA_ or KUBERNETES_ names, or generated service connection variables.

Unknown fields fail validation. GitHub shows inferra/account-config for account changes, inferra/config for app repositories and inferra/deploy/<app> for deployment. An invalid replacement keeps the last accepted configuration. A successful parse alone does not prove every optional feature is available.

Existing repositories

Back up data and review the migration instructions before switching an existing deployment. inferra init --migrate --account ACCOUNT --repo REPO is the migration entry point; inspect its output before merging. Changing files or bindings does not copy data. Create replacements, copy and verify data, switch bindings, then remove old services. Unbind apps before removing an account service file. For migration or restore help, email support@inferralab.com.
