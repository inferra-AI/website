Operate your apps

Git declares your apps and resources. Use the dashboard and CLI to operate the workloads already running.

Git owns configuration

Change configuration in Git and push. The dashboard and CLI inspect and operate the apps you declared.

  • Branches, repo teams, shared env and branch resource quotas: .inferra/repo.yaml on the default branch.
  • Build, run settings, sizing and service bindings: each app folder’s .inferra/app.yaml from the deployed branch.
  • Account quotas, repo allocations and team defaults: account.yaml at the root of the private <account>/.inferra repository.
  • Account services: services/*.yaml in that private repository. A GitHub admin must merge changes there.

Secret names belong in repo.yaml or app.yaml. Supply values through the dashboard, inferra secrets set APP NAME or selected-secret GitHub sync. See secret setup.

Choose the app

In the dashboard, open the repository org, its branch space, then the app. CLI examples below use an app folder named api. Set the target first:

inferra login
inferra target shop/main
inferra apps
inferra apps status api

Scale by changing app.yaml

Edit api/.inferra/app.yaml. For a fixed-size app:

version: 3
name: api
type: web
port: 3000
instances: 2
cpu: 0.5
memory: 512Mi

Commit and push the branch. Check its repo.yaml resource quota, account allocation and billing. Inspect the result with inferra instances api. For supported autoscaling, use a scale map instead of instances; request-based scaling with min above zero is not implemented.

Roll back an image

In the app overview, choose Roll back for the previous deployment, or open Deployments and choose Roll back on an earlier deployment that went live.

inferra deployments api
inferra rollback api
inferra rollback api --to DEPLOYMENT_ID

Rollback redeploys the earlier image. It keeps the current runtime configuration, environment and secret values; it does not restore an old configuration or database. The next eligible push deploys from the pushed commit again, subject to build selection and validation.

Promote the tested image

Promotion deploys the same image in another space without rebuilding, using the target app’s environment and secrets. Both spaces must be on the same cluster; the source deployment must have gone live, and you need developer access to both spaces.

The dashboard has Promote from… and Promote source → target controls in the earlier app view. The current tabbed app view does not expose these controls; use the CLI:

inferra promote api --from staging --space main
inferra promote api --from staging --to main --deployment DEPLOYMENT_ID

Restart, stop and start

Use the app header’s Restart or Stop button. A stopped app shows Start. Restart uses the same image. Stop removes running instances while keeping the URL, configuration and services. These operations require developer access.

inferra restart api
inferra stop api
inferra start api

Set secrets and inspect names

Open the app’s Settings tab. Under Secrets, choose Set value for a missing value or Replace for an existing value. The dashboard requests a restart so running instances receive the new value. Declare runtime secret names in repo.yaml or app.yaml. Values are never returned by secret read APIs.

The CLI lists names and can set values from stdin:

inferra env api
inferra env api --reveal
inferra secrets api
printf %s "$API_KEY" | inferra secrets set api API_KEY

--reveal requires developer access and reveals only ordinary environment values. Managed-service connection values remain hidden. Settings lists environment and secret names.

Logs, metrics and exec

Open the app’s Logs or Metrics tab. See Metrics and logs for chart and live-log controls. The current dashboard has no exec terminal; use the CLI to run a command in a ready instance:

inferra logs api --follow
inferra metrics api --since 6h
inferra exec api -- sh
inferra exec api --pod POD_NAME -- printenv PORT

Exec requires developer access. Without --pod, the CLI selects the first ready pod. Read the complete CLI reference.
